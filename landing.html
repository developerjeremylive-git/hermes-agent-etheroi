Profundidad

Cómo funciona, en detalle

Hermes no es un wrapper sencillo. Es un agente completo con plugables, memoria, aprendizaje, y una arquitectura pensada para ser extendida.

Arquitectura y componentes internos

Hermes es el único agente con un bucle de aprendizaje integrado que funciona sin supervisión:

Creación de habilidades: tras tareas complejas, el agente detecta patrones y genera habilidades automáticas — scripts reutilizables, Knowledge que agrega a su base, y prompts especializados. Para verlas: /skills.

Auto-mejora: las habilidades no son estáticas. Durante el uso, el agente identifica mejoras, optimiza prompts, y refina sus respuestas. Cada sesión es una iteración más.

Memoria persistente: información relevante se guarda en bases de datos (SQLite con FTS5) y en memorias semi-estructuradas. El agente construye un modelo cada vez más profundo de quién eres — tus preferencias, proyectos, estilo de trabajo.

Búsqueda de sesiones: FTS5 sobre el historial de conversaciones + resumen por LLM para recuperar contexto de sesiones pasadas. El agente puede decir "en nuestra conversación de la semana pasada mencionaste esto..."

El gateway es un proceso único que maneja todas las plataformas simultáneamente. No hay procesos separados por canal — uno solo, con toda la lógica centralizada.

Adapteres por plataforma: cada plataforma (Telegram, Discord, Slack, WhatsApp, Signal, Email, Webhook, Home Assistant) tiene su adaptador, todos ellos bajo gateway/platforms/. Nuevas plataformas se agregan sin tocar el core.

Continuidad cross-platform: una conversación puede empezar en Telegram, continuar en Discord, y terminar en CLI. El agente mantiene el contexto completo gracias a un sistema de sesiones unificado.

Transcripción de voz: notas de voz en Telegram y WhatsApp se transcriben automáticamente (STT) antes de llegar al agente — el agente "escucha" lo que dijiste.

Streaming: en plataformas que lo soportan (Discord, Slack), las respuestas se envían parcialmente en tiempo real, no de golpe al final.

Hermes tiene un sistema de plugins diseñado para extensión sin tocar el core. Hay tres categorías de plugins:

  • General plugins (plugins/<name>/): registran herramientas, hooks de ciclo de vida (pre_tool_call, post_llm_call, on_session_start, ...), y comandos CLI. Ej: kanban, observability, disk-cleanup.
  • Memory providers (plugins/memory/<name>/): backends de memoria. Incluidos: Honcho, mem0, supermemory, byterover, hindsight, holographic, openviking, retaindb. El standard está abierto — cada uno implementa la misma ABC.
  • Model-provider plugins (plugins/model-providers/<name>/): cada backend de inferencia es un plugin. Anthropic, OpenAI, OpenRouter, Nous Portal, Gemini, Mistral, etc. Todos se registran con register_provider().

MCP (Model Context Protocol): Hermes puede conectar servidores MCP externos para capacidades adicionales. Esto es lo que permite extender el agente sin modificar el código base.

Regla de política (May 2026): no se agregan nuevos plugins de terceros en-tree. Si tu plugin integra un producto externo (SaaS, dashboard, analytics), publica tu propio repo e instala en ~/.hermes/plugins/.

Hermes no está atado a un modelo. Puedes usar cualquier proveedor que quieras, e incluso mezclar varios:

  • Proveedores integrados: Anthropic, OpenAI, OpenRouter (300+ modelos), Nous Portal, Gemini, Mistral, Groq, LM Studio, Ollama, y más.
  • Cambio dinámico: /hermes model anthropic/claude-sonnet-4-20250514 o /hermes model openrouter/qwen-2.5-72b-instruct. Sin reiniciar, sin configurar.
  • Nous Portal: una suscripción única que cubre modelos, búsqueda web (Firecrawl), generación de imágenes (FAL), TTS (OpenAI), y navegador en la nube (Browser Use). hermes setup --portal para activarlo.
  • Smart model routing: configuración avanzada para routing por tarea — usa un modelo barato para tareas simples y uno potente para reasoning complejo.

El scheduler cron integrado permite tareas programadas con entrega a cualquier plataforma:

  • Formatos de schedule: duración ("30m", "2h"), "every" phrase ("every 2h", "every monday 9am"), expresión cron ("0 9 * * *"), o timestamp ISO para ejecución única.
  • Entrega: a la plataforma origen, a todas las plataformas conectadas, o a una específica. Continuidad para reporting persistente.
  • Scripts de recolección: cada tick puede ejecutar un script de datos que inyecta su salida en el prompt del agente — ideal para monitoreo, scraping, o reports de estado.
  • Sin agente (no_agent): para tareas script-only, el cron ejecuta el script y entrega el stdout directamente, sin invocar al LLM. Watches de memoria, disco, GPU, heartbeats.
  • Hard interrupts: 3 minutos de tiempo máximo por sesión cron para evitar loops runaway. Catch-up window y grace window para ticks perdidos.

delegate_task permite lanzar subagentes aislados para trabajo en paralelo:

  • Leaf agents: trabajadores enfocados, sin capacidad de delegar a su vez. Tienen su propio contexto, terminal, y herramientas.
  • Orchestrators: retienen delegate_task para spawnear sus propios workers (gated por delegation.orchestrator_enabled).
  • Batch paralelo: pasa tasks: [...] para ejecutar múltiples subagentes concurrentes. Capped por delegation.max_concurrent_children (default 3).
  • Background async: con background=true, Hermes devuelve un delegation id inmediatamente y el resultado re- entra en la conversación después.
  • Durability: la delegación es process-local. Para trabajo que debe sobrevivir al reinicio, usa cronjob o terminal(background=True).

Hermes tiene seis backends de terminal, cada uno con diferentes características de ejecución y persistencia:

  • Local: el terminal de tu máquina, con todas las capacidades del sistema.
  • Docker: ejecución aislada en contenedor — ideal para seguridad y reproducibilidad.
  • SSH: conecta a un servidor remoto y ejecuta comandos allí.
  • Singularity: contenedores HPC y entornos de investigación.
  • Modal: serverless con persistencia — el entorno hiberna cuando está inactivo y se activa bajo demanda, costando casi nada entre sesiones.
  • Daytona: similar a Modal, entornos cloud con persistencia y zero-cost cuando idle.

Terminal integrado en la app de escritorio: Electron con terminal real, no solo un widget. Permite ejecutar comandos mientras chateas.

Hermes maneja sesiones persistentes con una base de datos SQLite (FTS5) que permite búsqueda full-text sobre todo el historial:

  • SessionDB: cada conversación es una sesión con ID único, título auto-generado, y historial completo de mensajes.
  • FTS5 search: busca en conversaciones pasadas con consultas booleanas, frases exactas, y wildcards. El agente puede recuperar contexto de sesiones antiguas.
  • Context compression: cuando el contexto se vuelve muy largo, el agente puede comprimirlo manteniendo lo relevante — sin perder información importante.
  • /perfiles: múltiples instancias completamente aisladas, cada una con su propio HERMES_HOME (config, API keys, memoria, sesiones).
  • Archivos de contexto: AGENTS.md y CLAUDE.md en el directorio de trabajo dan contexto de proyecto al agente.
Bots · Delegación

Un bot dentro de otro: tu agente, multiplicado

Hermes no es un bot — es un agente que puede invocarse a sí mismo. Lanza subagentes especializados, en paralelo o en cadena, para delegar work, investigar, o ejecutar tareas en aislamiento. Cada subagente es un agente completo con su propio contexto, terminal, y herramientas — y el padre recibe solo el resumen final.

🌳

Árbol de delegación

subagentes anidados

Cada agente puede spawnear subagentes. Por defecto el árbol es flat (1 nivel), pero se puede profundizar a 2+ niveles configurando delegation.max_spawn_depth.

  • Padre (root): construye el árbol, coordina resultados
  • Hijo level 1: worker enfocado, 병목 없음
  • Nieto level 2: orquestador que further decompose (si depth >= 2)
  • Cada nivel recibe solo el contexto necesario — no todo el historial
🎭

Dos roles, dos responsabilidades

leaf · orchestrator

Cada subagente nace con un rol que determina si puede delegar a su vez:

  • Leaf (default): trabajador enfocado. No tiene la herramienta delegate_task — no puede spawnear. Recibe el goal, hace el work, devuelve el resumen.
  • Orchestrator: retiene delegate_task y puede spawnear sus propios workers. Útil cuando un goal se descompone en subtareas paralelas.
  • Cómo se asigna: pasa role="orchestrator" en delegate_task. Si delegation.orchestrator_enabled=false, todas las peticiones se coercian a leaf.
⚡

Batch paralelo

múltiples subagentes simultáneos

Pasa tasks: [...] con varios goals independientes — cada uno corre en su propio subagente concurrentemente, sin esperar al anterior.

  • Config: delegation.max_concurrent_children (default 10, pero el sistema recomienda 3 para control)
  • Casos de uso: research A + B en paralelo, análises de múltiples archivos, pruebas en distintos entornos
  • El padre espera: todos los hijos deben terminar antes de que el padre siga — recibe todos los summaries juntos
  • Background: con background=true, el padre no espera — el resultado re-entra en la conversación cuando esté listo
🔒

Aislamiento fuerte

contexto fresco · herramientas bloqueadas

Cada subagente tiene su propio contexto — nada del historial del padre se filtra. Además, herramientas peligrosas o de side-effect se bloquean automáticamente:

  • delegate_task — no recursión infinita
  • clarify — no interacción con el usuario
  • memory — no escritura en MEMORY.md compartido
  • send_message — no side effects cross-platform
  • cronjob — no scheduling de más trabajo
  • Terminal: el subagente tiene su propia sesión de terminal aislada (task_id propio)
🛠️

La herramienta delegate_task

tool call · schema completo

El modelo invoca delegate_task como un tool call normal. Tiene dos formas:

  • Single: goal + opcional context, toolsets, model, role. El subagente corre y el padre espera el summary.
  • Batch: tasks: [{goal, context, ...}]. Múltiples subagentes paralelos, cada uno con su propio goal.
  • Control post-spawn: los ids de los subagentes se devuelven en la respuesta. Luego puedes action="list", action="steer", o action="stop" sobre ellos.
🎯

Steer e Interrupt

control en tiempo real

Una vez spawneado, un subagente se puede controlar sin detenerlo:

  • Steer: action="steer" + message. El texto se encola y el subagente lo ve en su siguiente tool result — nunca corta una tool call en curso. Útil para corregir rumbo sin perder trabajo.
  • Interrupt: action="stop". Solicita una parada limpia al next iteration boundary. Las tool calls en vuelo son notificadas para cancelarse. El resultado parcial aún se entrega.
  • List: action="list". Snapshot de todos los subagentes vivos: id, parent_id, depth, goal, model, status, running_seconds, live_transcript.
⚙️

Configuración de delegación

config.yaml · delegation.*

Todas las boundaries de delegación se configuran en config.yaml bajo delegation::

  • max_concurrent_children: 3 — cuántos hijos simultáneos como máximo
  • max_spawn_depth: 1 — profundidad del árbol (1 = flat, 2 = permite nietos)
  • orchestrator_enabled: true — permite role="orchestrator" (si false, todo es leaf)
  • subagent_auto_approve: false — aprobación de comandos peligrosos en subagentes (default: denegar, evitar deadlocks de TUI)
  • child_timeout_seconds — timeout por subagente
  • inherit_mcp_toolsets — si el hijo hereda las herramientas MCP del padre
📋

Casos de uso reales

cuándo delegar

La delegación no es magia — es la herramienta correcta para ciertos patrones de trabajo:

  • Investigación paralela: "investiga X y Y simultáneamente" → 2 subagentes leaf, cada uno en una query, padre sintetiza
  • Análisis de codebase: "lee y analiza los archivos A, B, C en paralelo" → batch de 3 subagentes
  • Tareas de ejecución pesada: compilación, test suite, data pipeline → subagente con terminal, padre no se satura de output
  • Orquestación compleja: goal que se descompone en 3+ subtareas interdependientes → orchestrator level 1 spawnea 3 leaves, sintetiza
  • Work variado: "investiga + escribe + prueba" → 3 subagentes con toolsets distintos (web, file, terminal) en paralelo
Límite de profundidad (MAX_DEPTH = 1 por defecto): por seguridad y costo, el árbol es flat — el padre spawnea leaves, y los leaves NO pueden spawnear a su vez. Para árboles de 2+ niveles, configura delegation.max_spawn_depth >= 2 y usa role="orchestrator". Cada nivel adicional multiplica el costo de API tokens, así que el default conservador es deliberate.
Historia · Evolución

De prototipo a agente autoconsciente

Hermes ha evolucionado desde un CLI experimental hasta un agente completo con aprendizaje, memoria, y soporte para múltiples plataformas — todo sin dejar de ser open source.

v0.1 — Orígenes

CLI experimental

Primera iteración: un agente de terminal con soporte para modelos básicos y herramientas simples. La base del bucle de conversación.

v0.5 — Gateway

Gateway de mensajería

Introducción del gateway unificado: un solo proceso que maneja múltiples plataformas. Primera integración con Telegram y Discord.

v0.10 — Plugins

Sistema de plugins

Plugins de memoria, model-providers, y herramientas personalizadas. El core se mantiene narrow; la capacidades vive en los edges.

v0.15 — Learning Loop

Bucle de aprendizaje integrado

Creación automática de habilidades, memoria persistente, y búsqueda FTS5 de sesiones. Hermes comienza a ser "autoconsciente".

v0.18 — Desktop

App de escritorio + TUI

Hermes Desktop (Electron) y TUI completa en React + Ink. Terminal integrado, chat en vivo, y slash commands.

v0.20 — Expandir

Multi-plataforma completa + serverless

Soporte para WhatsApp, Signal, Email, y webhooks. Backends de terminal serverless (Modal, Daytona). Cron, kanban, y más de 40 herramientas.

Próximos pasos: seguimos expandiendo el sistema de plugins, agregando más backends de terminal, e investigando capacidades de investigación (batch trajectory generation, compression para entrenar la próxima generación de modelos de tool-calling).
